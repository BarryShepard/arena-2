# 2D Arena: проверка требований и договорённости MVP

Исходное требование пользователя: локальная top-down PvP-арена, в которой персонажи являются файловыми модами с собственными ассетами, состоянием и четырьмя программируемыми способностями. Главное доказательство — существенно новая механика без изменения ядра. Этот документ уточняет неоднозначности, не заменяя исходный запрос.

## Вывод

Концепция внутренне согласована. Риск — превратить перечень потенциальных механик в обязательный объём первого релиза. Неограниченную выразительность невозможно доказать конечным набором примитивов: MVP должен доказать её на трёх существенно разных модах и четвёртом изменении, которое затрагивает только файлы мода.

## Решения для первого прототипа

1. **Среда запуска.** Браузер, Canvas 2D, локальный сервер разработки. После установки зависимостей игра работает без внешних сервисов. Открытие `index.html` через `file://` не является способом запуска. Команда запуска и URL должны быть в README.
2. **Управление.** Два игрока на одной клавиатуре: P1 WASD + F/G/H/J; P2 стрелки + Num1/2/3/0 с альтернативой I/O/P/[ для клавиатур без numpad. Движение плавное в четырёх направлениях, без диагоналей и привязки позиции к клеткам. При нескольких удерживаемых направлениях действует последнее нажатое; после его отпускания — предыдущее удерживаемое. Взгляд сохраняет последнее ненулевое направление движения. Это правило обычного управления не запрещает модам создавать произвольные векторы импульсов, снарядов и перемещений способностями. Это осознанное ограничение MVP; независимый twin-stick прицел и геймпады — следующий шаг, если бой покажет необходимость. Все привязки указать в интерфейсе; использовать физические `KeyboardEvent.code`. Поддержать переназначение через простой конфиг; ограничения одновременных нажатий клавиатуры не решаются программно.
3. **Ввод способностей.** Ровно четыре слота, события `press`, `hold`, `release`; автоповтор клавиатуры не создаёт повторный `press`. Состояние, заряды и cooldown принадлежат моду, движок только показывает переданные подписи и состояния слотов.
4. **Кто побеждает.** У каждого участника есть один или несколько живых тел с флагом `countsForDefeat`. Победа проверяется после обработки всех событий смерти текущего тика и созданных ими сущностей. Обычный summon флага не имеет; дочерние тела weird-персонажа имеют. Нет живых тел у обоих — ничья. Отложенное воскрешение после признанного поражения в MVP не поддерживается. Так смерть основного тела совместима с распадом на живые части.
5. **Владение.** Каждая сущность имеет неизменяемый владельцем модом `ownerId`, команда совпадает с участником. Мод управляет своими сущностями, читает снимок мира, воздействует на противника через команды урона, импульса и статусов. Создание клона не создаёт новую VM. Один runtime на участника: mirror match не разделяет mutable state. Группа тел может получать общий input по решению скрипта.
6. **Модель мира.** Фиксированный шаг 1/60 секунды; координаты и секунды в мировых единицах. Круглые collision/hitbox, границы арены; отдельно solid-body и sensor/hurtbox. Hitbox не обязан равняться размеру картинки. Нужны overlap circle, segment/raycast, положение/скорость/импульс, HP, таймеры, lifetime, generic entities и визуальные эффекты. Projectile — обычная сущность с движением и реакцией на контакт, а не закрытый тип способности.
7. **Порядок событий.** Input → callbacks/timers → движение и контакты → очередь попаданий/урона → очередь смертей/spawn → проверка победы → render snapshot. `beforeHit` позволяет отменить/изменить попадание, `damageReceived` сообщает реально снятые HP, `death` вызывается один раз. Очередь FIFO с техническим бюджетом; новые события не вызываются рекурсивно. Объект с HP=0 перестаёт наносить контактный урон, но его death callback может создать взрыв. Взрывы могут привести к ничьей.
8. **Формат мода.** `characters/<id>/manifest.json`, `main.js`, `sprites/*.png`, `effects/*.png`, `sounds/*.wav`. PNG sprite sheets задают размер кадра, число кадров и FPS. WAV — достаточный звуковой формат MVP. Версия API обязательна. Никакого списка имён demo-персонажей в ядре или ручного registry: сервер автоматически обнаруживает директории; Reload заново читает файлы до нового матча. Импорт выбранной папки через browser file input — удобное дополнение, не обязательное условие.
9. **Скриптинг.** JavaScript внутри QuickJS/WASM с явным JSON API. Не выполнять пользовательский код через host `eval`, `new Function`, Node `vm` или обычный import. Не предоставлять DOM, сеть, файловую систему, произвольную загрузку модулей. Отдельные ограничения памяти/стека/CPU, количества сущностей/таймеров/эффектов/событий и размеров команд. При превышении остановить матч с диагностикой мода и возможностью вернуться в выбор персонажей. Это техническая ошибка, не поражение из-за силы персонажа.
10. **VFX.** PNG-кадры и простые геометрические эффекты: в точке, на сущности, между двумя точками; angle, scale, duration, loop, fade; звук и shake. Небольшой sequence helper связывает задержки, команды и эффекты через игровые таймеры. Нет редактора timeline и promise-based фоновых действий, продолжающих жить после матча.

## Уточнения пользователя после первого плана

- **Визуальный и пространственный ориентир:** Tank 1990 NES — основа графики, поля и передвижения. Для MVP: компактное поле целиком на экране, контрастная тайловая поверхность, простые кирпичные препятствия и читаемые проходы, собственные пиксельные ассеты. Разрушаемость стен, база, волны врагов и остальные правила референса не следуют автоматически из этого пожелания. Проходы должны позволять стартовым телам двигаться; growth может создавать ограничения размера.
- **Продолжительность:** 180 секунд игрового времени, видимый отсчёт `3:00` → `0:00`. Пауза/скрытая вкладка не расходуют время. Restart сбрасывает таймер. Ранняя победа при гибели участника сохраняется. На последнем тике сначала разрешить урон и смерть, затем исход по таймауту.
- **Подтверждено пользователем:** если после разрешения событий последнего тика оба участника живы, матч заканчивается ничьей; сравнения HP и овертайма нет. Движение в четырёх направлениях без диагоналей. Визуальный ориентир, широкие проходы и отсутствие разрушаемости стен в первом этапе также согласованы.

## Три демо

- **Fighter:** направленный melee arc/sector через spatial query, рывок с ударом, заряжаемый тяжёлый удар (`press/hold/release`), круговой knockback. Его атаки и рывок полностью написаны в моде.
- **Mage:** projectile, двухфазная установка/использование teleport anchor, зона периодического урона, временная турель. Турель — скрипт сущности мода, а не AI opponent.
- **Bud/Weird:** растёт на 10% после реально полученного урона; первая смерть создаёт пять маленьких управляемых тел, которые продолжают матч. Четыре слота: выстрел всей группой, переключение плотного/широкого строя, живая мина, смена формы со сменой поведения первого слота. Дочерние тела не делятся повторно: это правило демо, не запрет движка. Максимальный размер демо ограничивается самим модом, чтобы персонаж оставался управляемым на арене.

## Что не обещает MVP

Не весь перечень потенциальных способностей должен быть реализован как демо. Не нужны сложные полигоны, полноценная физика, редактор модов, hot reload посреди боя, сетевой lockstep, AI opponents, установщик и автоматический баланс. Возможность новых механик расширяется generic API; абсолютная совместимость с любым будущим замыслом не гарантируется.

## Проверка результата

Автотесты доказывают контракт API, изоляцию, события, управление и lifecycle. Браузерная проверка доказывает загрузку/отрисовку/бой/restart. «Весело» остаётся гипотезой до короткого боя двух людей: оценить читаемость попаданий, возможность сближения/уклонения и удобство одновременного управления; не выдавать зелёные тесты за доказательство удовольствия от боя.

Основание выбора sandbox: [официальная документация QuickJSRuntime](https://github.com/justjake/quickjs-emscripten/blob/main/doc/quickjs-emscripten/classes/QuickJSRuntime.md) описывает отдельные runtime, interrupt handler, memory limit и stack limit. Это механизмы ограничения, не основание обещать абсолютную защиту; границы host bridge требуют отдельных тестов.
